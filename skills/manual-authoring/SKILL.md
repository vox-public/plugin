# manual-authoring

## Manual의 역할
Manual은 고객과 대화하는 음성 에이전트의 업무 절차다. 코파일럿을 위한 SKILL.md와 다르다. Single 에이전트의 기본 구성은 짧은 프롬프트 + 고객 의도별 Manual + 지식이다. 현재 에이전트 유형에서 지원하는 Manual 형식으로 작성한다.

## 어디에 쓸까
같은 규칙을 프롬프트와 Manual에 중복해 쓰지 않는다. 한 규칙은 한 곳에만 둔다.
- 프롬프트: 역할·말투·인사(`firstLine`/`firstLineType`)·모든 업무에 공통인 금지(예: 가격 확정 금지). 짧게 쓴다(대략 1,500자 이내).
- Manual: 특정 고객 의도에서만 필요한 절차·정책·예외·도구 호출 조건. 전역 규칙이면 프롬프트, 업무 한정 규칙이면 Manual이다.
- 지식: 바뀔 수 있는 사실과 FAQ(진료시간, 주소, 가격표). Manual에는 사실을 복사하지 않고 "진료시간은 지식에서 확인해 안내"처럼 출처만 쓴다.

## 몇 개로 나눌까
- 고객 의도(=트리거) 하나에 Manual 하나다. 첫 구축은 보통 2~5개다(예: 예약 접수 / 예약 변경·취소 / 진료 문의 / 응급·직원 연결).
- 여러 Manual이 공유하는 단계(직원 연결, 본인 확인)는 트리거를 비운 공용 Manual로 두고 각 Manual 본문에서 `@manual:`로 참조한다.
- 본문은 8,096자 이하다. 넘거나 트리거가 둘로 갈리면 나눈다.
- 방향(인바운드/아웃바운드), 페르소나·목소리·번호가 다르면 Manual을 늘리지 말고 에이전트를 나눈다.

## 트리거 쓰기
트리거는 업무 이름이 아니라 고객이 처한 발화 상황으로 쓴다. 예: "예약 변경"보다 "이미 잡은 예약의 날짜·시간을 바꾸거나 취소하려는 고객". Manual끼리 겹치지 않게 쓰고, 범위 밖 요청이 어느 Manual에도 걸리지 않을 때의 응대는 프롬프트에 둔다.

## 작성 순서
1. 시작 조건과 처리 범위를 적고 알려진 사전 정보를 확인한다. 아웃바운드는 연락 이유·통화 가능 여부·거절을, 인바운드는 문의 목적·분류를 포함한다.
2. 목표 달성에 필요한 질문을 순서와 조건으로 표현한다. 이미 답한 내용은 재질문하지 않고 정정된 값으로 요약을 갱신한다.
3. 도구 호출 조건, 필요한 입력, 성공의 근거, 실패/무응답 시 대응을 함께 쓴다. 존재하지 않는 도구 참조나 예약 기능을 적지 않는다.
4. 종료 전 고객에게 확인할 요약과 실제 결과를 구분한다. 종료 동작은 현재 제품의 지원 참조 문법·내장 도구 설정으로 연결한다.

## 에이전트에 연결하기
1. `save_agent(mode=create)`에서 `type`은 생략하거나 `single_prompt`로 보내고, 업무에 맞게 다시 쓴 `data.prompt.prompt`를 넣는다. 템플릿으로 시작했다면 기본 프롬프트의 업종·방향·완료 문구(예: 아웃바운드 가정, "예약 완료됐습니다")가 새 Manual과 충돌하지 않게 고쳐 쓴다.
2. Manual마다 `save_manual(mode=create, agent_id, payload={expected_head_revision, name, trigger, content, built_in_tools})`를 호출한다. 이 호출이 곧 연결이다. `data.manuals` 맵이나 폐기된 `manualIds`를 손으로 만들지 않는다. 저장할 때마다 revision이 바뀌므로 다음 Manual 전에 현재 `head_revision`을 다시 읽는다.
3. Manual의 `built_in_tools`(통화 종료·전환·문자 등)는 본문에서 `@tool:이름`으로 참조해야 실행된다. 참조하지 않은 도구는 통화에서 버려진다. 통화 종료처럼 모든 업무에 공통인 도구는 에이전트 `data.built_in_tools`에, 업무 한정 도구(전환·문자)는 해당 Manual에 둔다.
4. 저장 뒤 `list_manuals`로 `total_count`, 트리거가 있는 Manual(`is_entry`)의 수, 진단 건수(`diagnostic_count`)가 0인지 확인하고, `get_manual`로 본문이 참조하는 도구가 의도와 같은지 본다.

## 좋은 원고의 기준
‘친절히 처리한다’만 쓰지 말고 결정에 필요한 조건을 적는다. 가격·정책·가용 시간을 출처 없이 채우지 않는다. 도구의 성공 응답 전 완료를 약속하지 않는다. 필수 단계가 순서대로 실행됐는지는 실제 시험에서 확인한다. prose만으로 결정적 상태 머신을 만들었다고 말하지 않는다. 다만 순서가 중요하다는 이유만으로 Flow로 바꾸지 않는다. 필수 단계는 번호 단계·완료 조건·도구 성공 조건으로 쓴다. 유형 판단은 [voice-agent-design](../voice-agent-design/SKILL.md)의 ‘에이전트 유형 선택’을 따른다.

정정/정보 제공 거절/범위 밖 요청/도구 실패 중 업무에 해당하는 사례를 붙인다. 과거 원고를 분리할 때 각 규칙의 새 위치를 표시하고 빠진 종료·예외를 점검한다.

저장은 [edit-manual-safely](../edit-manual-safely/SKILL.md), 근거 자료 정리는 [knowledge-grounding](../knowledge-grounding/SKILL.md)를 사용한다.
