# post-call-result-design

## 세 가지 결과를 구분한다
수집 사실, 업무 성공 여부, 외부 시스템의 실제 완료는 별개다. ‘희망일을 들었다’가 ‘예약이 확정됐다’는 뜻은 아니다. 추출 필드 설명은 발화에서 무엇을 찾아야 하는지, 평가 기준은 무엇이 성공인지 설명한다.

## 필드 설계
사용 목적이 있는 항목만 제안한다. 타입·선택값·미수집/거절/모름의 의미를 정하고 실제 제품 스키마가 지원하는 표현을 확인한다. 필드별 처리 방식과 글자 제한은 실제 제품 계약에서 확인한다.

정정된 최종값을 저장할지, 여러 후보 중 하나를 선택할지 명확히 한다. 정해진 필드가 서로 모순될 때의 판단은 통화 근거에 두고 임의의 기본값으로 누락을 숨기지 않는다. 조기 종료로 단계에 도달하지 않은 경우와 업무 실패를 분석에서 분리한다.

## 검증 예
합성 사례: 날짜를 수요일에서 금요일로 정정했다면 최종 저장 결과와 요약이 일치해야 한다. 연락처를 거절했으면 임의 번호를 생성하지 않는다. 외부 예약 도구가 실패했으면 정보 수집이 성공해도 예약 성공으로 분류하지 않는다.

제품에 해당 평가 기능이 없으면 개발용 판정표로 남긴다. 별도 고객용 Tests 프로젝트를 만들지 않는다.

실제 설정 저장은 [configure-call-results](../configure-call-results/SKILL.md), 운영 수치 해석은 [review-call-performance](../review-call-performance/SKILL.md)로 연결한다.
