# manual-authoring

## 운영 수준 점검
Manual을 쓸 때 지키고, 저장한 뒤 `get_agent`·`get_manual`로 다시 읽어 하나씩 확인한다.
1. 질문 단계마다 "답이 없거나 불분명하면 한 번 다시 묻고, 그래도 안 되면 …" 가지를 둔다. 정보 제공 거절, 정정, 범위 밖 요청에도 할 행동을 적는다.
2. 도구 호출마다 언제·입력·결과별 행동(성공/없음/실패·지연)을 쓰고, "실패하면 다시 부르지 않고 …(메모·콜백·안내)"를 적는다. "완료·접수·전송했다"는 성공 결과를 받은 뒤에만 말한다. 전환·문자·등록처럼 부작용이 있는 도구는 고객이 동의한 뒤 부른다.
3. 순서가 중요한 곳은 게이트("…을 확인하기 전에는 …하지 않는다")로, 반복은 상한("최대 2회. 넘으면 …")으로 쓴다.
4. 상담원 연결·연락처 확인처럼 두 Manual 이상이 쓰는 단계는 공용 Manual 하나에 두고 `@manual:<id>`로 넘긴다. 마무리 인사 문장은 프롬프트 `# 마무리`에 한 번만 쓰고, Manual 완료 단계에는 결과에 맞는 종료 도구만 적는다.
5. 프롬프트에 둔 규칙(금지·말투·정해진 거절 문구)을 Manual에 다시 쓰지 않는다. 같은 대상(Manual·종료 도구)은 늘 같은 이름으로 부른다.
6. 내용이 가까운 형제 Manual의 트리거에는 "…은 제외한다(○○ 담당)"를 붙인다.
7. `{{변수}}`를 쓰면 `presetDynamicVariables`에 선언하고, 값이 비었을 때 할 말을 적는다.
8. 위급·안전 신호(통증·사고·누출 등)는 접수 Manual 끝에 묻어 두지 않고, 연결 도구를 가진 별도 진입 Manual로 둔다.

어긋난 곳은 같은 `manual_id`(또는 `agent_id`)로 고친 뒤, 사용자에게 "점검: ○○ 보완" 한 줄로 알린다.

## Manual이 통화에서 쓰이는 방식
- 에이전트는 Manual 목록(이름 + 트리거)을 본다. 대화가 **정확히 하나의** 트리거에 맞을 때, 또는 프롬프트가 그 Manual을 고르라고 할 때 연다. 둘 이상 맞거나 하나도 맞지 않으면 프롬프트 지시를 따른다. 트리거가 겹치면 아무것도 열리지 않을 수 있다.
- 열린 Manual 본문이 `@manual:<manual_id>`로 넘기라고 하면, 대상 Manual은 트리거가 맞지 않아도 열린다.
- Manual이 소유한 내장 도구는 그 Manual이 열려 있고 본문에 `@tool:이름`이 있을 때만 쓸 수 있다.
- Manual 이름·ID·도구 이름은 내부 정보다. 고객에게 말하지 않는다.

## 어디에 쓸까 (한 규칙은 한 곳에)
| 위치 | 담는 것 |
|---|---|
| 프롬프트 | 정체성·말투, 음성 발화 규칙(숫자 읽기, 내부 용어 금지), 모든 업무에 공통인 금지, **Manual 선택 우선순위**, 공통 마무리와 종료 도구 |
| Manual | 고객 의도 하나의 절차·분기·예외·도구 호출 조건·원문 문장 |
| 지식 | 바뀌는 사실: 운영시간, 주소, 가격표, 서류 목록, FAQ |
| 동적 변수 | 통화마다 다른 값: `{{customer_name}}`, 예약일. 비었을 때 할 말도 정한다 |

- 프롬프트는 보통 1,500~4,000자다. 이보다 길어지면 업무 절차가 프롬프트에 들어간 것이니 Manual로 옮긴다.
- Manual에 "프롬프트의 ○○ 절을 따른다"고 쓰지 않는다. 공통 규칙은 프롬프트가 늘 적용한다.
- 프롬프트의 "Manual 선택" 절에는 우선순위를 쓴다. 예: ① 위급·안전 ② 진행 중인 Manual 계속 ③ 트리거가 하나만 맞으면 그 Manual ④ 아무것도 맞지 않으면 용건을 한 번 묻는다.

## 몇 개로 나눌까
- 고객 의도 하나에 Manual 하나다. 운영 에이전트는 보통 3~10개다.
- 다음이면 나눈다.
  - 트리거가 "또는"으로 서로 다른 일을 묶는다.
  - 본문이 5,000자를 넘는다(한도 8,096자).
  - 같은 단계가 두 Manual 이상에 필요하다. 예: 상담원 연결, 본인 확인 → 공용 Manual.
  - 큰 분기 하나가 길다 → 하위 Manual. 이름은 `예약 > 비용 안내`처럼 쓴다.
- 다음이면 합치거나 옮긴다.
  - 질문 순서와 도구가 같고 안내 문장만 다르다 → Manual 하나 안에서 분기한다.
  - 사실 안내뿐이다 → 지식으로 옮긴다.
- 방향(인바운드/아웃바운드)·페르소나·번호가 다르면 Manual을 늘리지 말고 에이전트를 나눈다.
- 이름은 업무명으로 짓는다. "새 메뉴얼"처럼 비워 두지 않는다. 이름도 선택 목록에 들어간다.

## 트리거 쓰기
형식: `[진입 상황], [고객이 먼저 말하는 경우], 또는 [앞서 확인한 값을 정정할 때]. [제외: 형제 Manual 몫]`
- 고객이 실제로 쓰는 낱말과 동의어를 나열한다. 음성 인식 오류에 대비해 "말이 정확히 들리지 않아도 이런 낱말이 섞이면 이 Manual을 따른다"를 붙일 수 있다.
- 내용이 가까운 형제 Manual이 있으면 경계를 "…은 제외한다(○○ 담당)"로 적는다.
- 상태도 트리거가 될 수 있다. 예: "상담원 전환이 실패했을 때", "본인 확인 뒤 통화 가능하다고 답했을 때".
- 1~3문장, 60~250자 정도로 쓴다.
- 나쁜 예: "예약", "인사말 하기 전".
- 좋은 예: "이미 잡은 진료 예약의 날짜·시간을 바꾸거나 취소하려 할 때, 고객이 예약자 이름이나 날짜를 먼저 말할 때, 또는 앞서 말한 예약 정보를 정정할 때. 새 예약은 제외한다(진료 예약 담당)."
- 공용 Manual에도 트리거를 둔다(직접 요청 + 다른 절차에서 넘어온 경우). 연결로만 들어와야 할 때만 트리거를 비운다.

## 본문 템플릿
```
## 규칙
- 범위: 하는 일 / 하지 않는 일(→ @manual:<id>)
- 완료 조건: 무엇이 확인돼야 완료라고 말하는가
## 진행 절차
### 시작
1. 고객이 이미 말한 값은 확인만 하고 다음 단계로 간다.
### <단계 이름>
1. 질문 하나.
   - <조건>: <행동>
   - 답이 없거나 불분명하면 한 번 다시 묻는다. 그래도 안 되면 <행동>.
   - 말하기를 거절하면 <행동>.
### <도구 결과 처리>
1. 언제: <조건>. 입력: <값의 출처>. @tool:<이름 또는 tool_id>를 부른다.
   - 성공: <행동> / 없음: <행동> / 실패·지연: 다시 부르지 않고 <대안>.
### 완료
1. 완료 조건을 확인한 뒤 결과를 알리고, 마무리 인사 뒤 <종료 도구>.
```

## 단계와 분기를 산문으로 쓰는 법
조회·예약·결과 코드 분기가 많은 업무도 Single + Manual로 쓴다. 순서가 중요하다는 이유만으로 Flow로 바꾸지 않는다([유형 선택](../voice-agent-design/SKILL.md)). 이름 붙은 단계, 게이트, 반복 상한이 순서를 잡아 준다.
- 단계마다 이름을 붙이고, 이동은 "'단계 이름'으로 이동한다"로 쓴다. 이름과 번호가 상태 기계 역할을 한다.
- 한 턴에 질문 하나만 한다. 이미 들은 값은 묻지 않고, 정정되면 그 값만 고친다.
- 조건마다 번호를 붙여 행동을 적는다. "그 밖에"와 "답이 불분명하면" 가지를 반드시 둔다.
- 반복에는 상한을 둔다: "한 번만", "최초 포함 최대 2회". 넘었을 때의 행동도 적는다.
- 뒤에서 쓸 값은 "…을 기억한다"로 적는다. 의사가 바뀌면 가장 최근 의사를 따른다.
- 순서를 지켜야 하면 게이트로 쓴다: "본인 확인 전에는 계약 내용을 말하지 않는다".
- 다른 Manual로 넘길 때는 "이 절차를 멈추고 @manual:<id>를 시작한다"로 쓴다. 하위 Manual 끝에는 "원래 절차로 돌아간다"를 둔다.
- "적절히", "친절히"처럼 판단을 맡기는 말 대신 조건과 행동을 쓴다.

## 반드시·절대와 원문 문장
- 고객에게 할 말을 지정할 때는 큰따옴표로 쓴다. 프롬프트에 "큰따옴표 안 문장은 바꾸지 않고 그대로 말한다"를 한 번 둔다.
- 사용자가 준 문구는 다듬지 않고 그대로 옮긴다.
- 채울 자리는 `[날짜]`처럼 대괄호로 쓰고 "대괄호는 실제 값으로 바꿔 말한다"를 적는다.
- 금지 규칙에는 경계를 붙인다. 예: "금액을 말하지 않는다. 비용 문의는 담당자 확인으로 안내한다."
- 고지문 전체를 정해진 순서로 그대로 읽는 것이 업무의 중심이면 Flow를 검토한다([voice-agent-design](../voice-agent-design/SKILL.md) F2). 문장 몇 개만 고정이면 Manual로 충분하다.

## 도구 쓰기 (@tool)
- 내장 도구(`end_call`, `transfer_call`, `send_sms`, `transfer_agent` 등)
  - 그 Manual의 `built_in_tools`에 넣고 본문에서 `@tool:이름`으로 부른다.
  - 이름은 에이전트 안에서 고유한 영문이다(`[a-zA-Z_][a-zA-Z0-9_]*`).
  - 도구 `description`에는 호출 조건을 한 줄로 쓴다.
- API 도구: `@tool:<tool_id>`로 부른다. `list_tools`/`save_tool`이 돌려준 UUID를 쓴다. 없는 도구를 지어내지 않는다. 도구가 없으면 그 공백을 사용자에게 말한다.
- 도구 호출마다 네 가지를 적는다.
  1. **언제**: 조건, 그리고 필요하면 고객 동의.
  2. **입력**: 각 값을 어디서 가져오나(고객 발화, 앞 결과, 변수).
  3. **결과별 행동**: 성공, 값마다, 없음, 실패, 지연을 각각 처리한다.
  4. **다시 부르지 않을 조건**: 중복 호출과 재접수를 막는다.
- "완료"·"접수됐다"·"보냈다"는 성공 결과를 받은 뒤에만 말한다. 지연이나 오류 뒤에는 같은 쓰기 도구를 자동으로 다시 부르지 않는다.
- 문자: 고정 링크면 static으로 보낸다. 동의를 받은 뒤 호출하고, 실패하면 말로 안내할 대체 경로를 둔다.
- 전환
  - 연결 질문에 고객이 긍정한 뒤에 호출한다.
  - 대기 멘트는 도구가 말하므로 같은 말을 반복하지 않는다.
  - 실패하거나 상대가 받지 않으면 메모·콜백 같은 대안으로 넘어간다. 같은 통화에서 두 번 실패하면 더 시도하지 않는다.
- 종료
  - 결과를 나눠 보고 싶으면 결과마다 `end_call`을 하나씩 둔다(`finish_booked`, `finish_callback` 등, description에 결과를 쓴다).
  - "상태 → 종료 도구" 대응을 Manual 안에 적는다.
  - 종료 도구에 작별 인사가 설정돼 있으면 따로 인사하지 않는다.
### 주소 수집 패턴
- 방문·배송·출동처럼 주소를 업무에 쓰면 해당 Manual의 `built_in_tools`에 내장 `search_address`를 붙이고 본문에서 `@tool:search_address`로 부른다(설정 형식은 현재 저장 schema 확인).
- 단계: 고객이 말한 도로명·건물번호, 지번 또는 건물·장소명 단서 받기 → `@tool:search_address` → 후보를 읽어 주고 고객 확인받기 → 확인된 주소와 상세 동·호를 업무의 저장 도구에 전달한다.
- 도구는 주소를 확정하거나 저장하지 않는다. 고객 확인이 확정이며, 저장 성공 응답 전에는 접수 완료라고 말하지 않는다.
- 후보가 여럿이면 지역·도로명·건물번호 등 구분 단서를 한 번 더 받고 보완된 단서로 조회한 뒤 선택 후보를 고객에게 확인받는다. 그래도 모호하면 원문과 '확인 필요'를 남긴다.
- 후보가 0건이면 다시 말해 달라고 한 번 요청하고 보완된 단서로 조회한다. 그래도 없으면 받은 그대로 접수하고 '확인 필요'로 남긴다. 도구 오류·지연은 자동 재호출 없이 원문과 '확인 필요'를 남긴다.
- `recommended_action`이 `single_confirm_top_candidate`이면 최상위 후보를 읽고 확인받으며, `ask_disambiguation`이면 후보 차이를 설명하고 구분 단서를 한 번 받는다.
- `ask_for_core_address`이면 시·군·구와 도로명·건물번호 또는 지번 등 핵심 단서를 한 번 보완하고, `no_hit_retry`이면 위 0건 절차를 따른다. 실제 응답에 없는 값은 추측하지 않는다.

- 모든 업무에 공통인 종료 도구는 에이전트 `data.built_in_tools`에, 업무에서만 쓰는 도구는 해당 Manual에 둔다.
- 내부 ID·코드·필드명은 읽지 않는다. 고객이 받아 적어야 하는 번호만 한 자리씩 읽는다.

## 저장 순서와 확인
1. `save_agent(mode=create)`로 Single을 만든다(`type`은 생략하거나 `single_prompt`). 모델 선택과 구 API 예외는 [에이전트 구축의 모델 선택 규칙](../build-first-voice-agent/SKILL.md#모델-고르기)을 따른다. 템플릿으로 시작하면 생성 직후 현재 revision을 읽고 선택한 모델을 적용한다. 프롬프트에는 공통 규칙과 Manual 선택 절을 넣는다. 템플릿으로 시작했다면 기본 프롬프트의 업종·방향·완료 문구가 새 Manual과 충돌하지 않게 고쳐 쓴다.
2. 다른 Manual이 `@manual:`로 가리킬 대상(공용 상담원 연결, 하위 Manual)을 **먼저** `save_manual(mode=create)`로 저장해 `manual_id`를 받는다. 그다음 참조하는 Manual을 저장한다. 서로 가리키는 경우에는 먼저 저장한 뒤 `mode=update`로 전체 본문을 다시 보낸다.
3. `save_manual` 호출이 곧 에이전트에 연결하는 일이다. `data.manuals` 맵이나 폐기된 `manualIds`를 손으로 만들지 않는다. 저장할 때마다 revision이 바뀌므로 매번 직전에 읽은 `expected_head_revision`을 쓴다.
4. 저장한 뒤 확인한다.
   - `list_manuals`: `total_count`, 트리거 있는 Manual(`is_entry`) 수, 모든 `diagnostic_count == 0`.
   - `get_manual`: 참조 도구·Manual이 의도와 같은지 본다.
5. 실제 통화 시험 전에는 "저장·확인 완료, 시험 전"으로 보고한다.

## 피할 것
- 한두 줄짜리 Manual. 완료·실패·예외가 없으면 Manual이 아니다.
- 사실만 나열한 Manual(→ 지식). 문장만 다른 같은 Manual 여러 개(→ 하나로 합치고 분기).
- `@tool` 없이 "○○ 도구를 호출한다"고 쓰기. 본문에 전화번호·가격·주소를 직접 쓰기(→ 지식·변수).
- 프롬프트와 Manual에 같은 규칙을 두 번 쓰기. "프롬프트의 ○○ 절"을 가리키기.
- 겹치는 트리거, 제외절 없는 형제 Manual.
- 도구 결과를 받기 전에 완료 안내하기. 실패 뒤 같은 쓰기 도구를 다시 부르기.
